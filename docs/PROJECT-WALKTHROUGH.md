# Operations and Architecture Guide

## Processing flow

1. The browser/API creates a draft expense against an active employee reference.
2. Submission moves a draft to Pending approval and records a workflow event.
3. A Manager or Finance Administrator may approve or reject a pending claim. Self-approval is blocked; rejection requires a reason.
4. Finance Operator or Finance Administrator may separately post an approved claim in the local demo ledger. Posting is idempotent by transaction identifier.
5. The batch (triggered from the Batch operations page) runs the COBOL programs `EXPDEDUP`, `MATCH2`, `EXPVALID`, `EXPTOTAL`, `EXPRPT` and `CNTCHECK` as server processes under GnuCOBOL. It independently sorts, removes exact duplicate records, matches employee IDs, validates amount/date/category fields, and produces report, exception, summary, audit, and checkpoint files. It does not post expense workflow claims.

## Data and workflow boundaries

`data/EMPLOYEE.MASTER` is the sample employee source for the local pipeline. New local workflow employee records are stored in `data/workflow-demo.json`. Transaction input and batch output remain local text datasets in `data/`. These local files are demonstration storage, not authoritative DB2 or VSAM data. There is no synchronization between the local workflow expense list and the existing fixed-width transaction dataset.

The browser uses a local demo username/password login. The server derives the actor from an HttpOnly session cookie and performs permission plus object-scope checks. Demo identities are explicitly generated by `npm run demo:bootstrap`; they are not enterprise identity or production SSO. See `RBAC.md` for its session and deployment limits.

## Batch control equation

For every raw input record, the pipeline accounts for exactly one of: removed exact duplicate, unknown/inactive employee exception, matched field-validation rejection, or valid report candidate. Therefore:

`raw input = duplicates removed + unknown employee + validation rejects + valid candidates`

On successful report control, `valid candidates = report output`. On the intentional mismatch branch, report output is one less than valid candidates and RC=12; the report dataset is removed. The local pipeline currently matches employee presence but does not carry an employment status field in the 80-byte employee master, so inactive status requires a future extended reference-data contract.

## Return codes and outputs

- RC=0: report count matches, no exceptions.
- RC=4: report count matches, one or more records were sent to exceptions.
- RC=12: count-control failure; report is not retained.

Output datasets include `EXPENSE.DUPS`, `EXPENSE.CLEAN`, `EXPENSE.MATCHED`, `EXPENSE.VALID`, `EXPENSE.REJECT`, `EXPENSE.CATEGORY`, `EXPENSE.MONTHLY`, `EXPENSE.AUDIT`, and `EXPENSE.CHECKPOINT`; `EXPENSE.REPORT` is retained only when the count check passes.

## Mainframe boundary

COBOL/JCL/REXX/DB2/VSAM/RACF sources are templates that need an authorized site environment, adaptation, compilation/submission, and JES/DB2 evidence before they can be described as validated. The Node server never claims to execute z/OS programs. Review `MAINFRAME-SETUP.md` and `mainframe/db2/README.md` before site use.
